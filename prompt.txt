# PART 0 — LOCKED DECISIONS FOR WEEK 2

### ADR-006: Local disk storage, not S3, for Week 2
Recordings are stored on local disk under `backend/uploads/recordings/`, gitignored. S3
integration is explicitly Week 7 ("deploy backend/database/storage services") — do not add AWS
SDK or credentials this week.

### ADR-007: Audio-only recording. No video is captured or stored.
The webcam video stream is shown live in the browser (`<video>` element, `getUserMedia`) purely
as a self-preview for the candidate — it is never recorded, uploaded, or analyzed this week.
Only the audio track is captured via `MediaRecorder`. This matches the plan exactly: no
member's Week 2 task involves facial landmarks, head pose, or video processing. Confidence
scoring this week is a defined schema with clearly-labeled sample data (see Part 5.4), not real
video ML.

**Open concern, not resolved here — flag to your team/instructor:** none of the seven weeks in
your implementation plan explicitly schedule the Dlib/OpenCV/`solvePnP`/MediaPipe work described
in your technical spec, even though MediaPipe appears in Member 3's tech stack table. Someone
needs to decide which week actually builds real video-based confidence scoring. Record this as
an open item in `docs/week2-report.md`.

### ADR-008: faster-whisper is in scope this week, minimally
Use `faster-whisper` with the smallest practical model (`tiny.en` or `base.en` — English-only,
CPU inference) to produce a transcript with word-level timestamps. This is the only thing the
library does. WPM and filler-word counting are hand-rolled on top of its output — the library
gives you words + timestamps (the spectrogram-equivalent of raw data), the arithmetic and the
filler-word matching are yours, same distinction as Week 1's from-scratch policy.

### ADR-009: Bundled ffmpeg, not a system dependency
Use the `ffmpeg-static` npm package (bundles a static ffmpeg binary) with `fluent-ffmpeg` in the
backend, specifically to avoid a repeat of Week 1's environment-install pain (Python 3.11, CRLF,
etc.). Do not require the developer to install ffmpeg system-wide. If `ffmpeg-static` fails to
resolve a working binary on this machine, that's a real `DECISION REQUIRED` — don't silently
fall back to assuming system ffmpeg exists.

### ADR-010: Recording pipeline is synchronous, not queued
No Celery/Redis/job queue this week (ADR-001 from Week 1 still stands — no new async
infrastructure). The upload endpoint calls the ML service directly and waits for the full
result, with a generous timeout (see Part 3.3). This means upload response times may be several
seconds to tens of seconds depending on recording length — the frontend must show a real loading
state, not fake instant results. A background job queue is an explicit candidate for a later
week if this becomes a UX problem; don't add one yet.

### Format pipeline (locked)
Browser records `audio/webm;codecs=opus` -> uploaded to backend as multipart -> backend converts
to 16kHz mono WAV via ffmpeg-static -> forwarded to the **existing, unchanged** ML service
`/api/v1/audio/features` endpoint from Week 1, plus the new `/api/v1/evaluate` endpoint (Part
5.3) for the full scored result. **Do not modify the Week 1 `/api/v1/audio/features` contract —
it stays exactly as approved.**

### Caps (locked)
- Max recording duration: 300 seconds (5 minutes)
- Max upload size: 50 MB (raw webm, pre-conversion)
- Reject anything over either cap with a clear error before attempting conversion

# PART 3 — ML SERVICE: TRANSCRIPT, FLUENCY, SAMPLE CONFIDENCE (Members 3 & 4)

### 3.1 New dependency

### 3.2 `app/features/transcript.py`

`transcribe(wav_path: str) -> dict` — loads the `tiny.en` (or `base.en`, your call, document
which and why in `docs/ml-feature-notes.md`) model **once at module load**, not per-request
(loading it per-request will make every single call unusably slow). Returns:
```python
{
  "fullText": "...",
  "words": [ {"word": "so", "start": 0.42, "end": 0.61}, ... ]
}
```
Raise a clear exception if the audio has no detectable speech (empty `words`).

### 3.3 `app/core/filler_words.py`

A fixed, named list:
```python
FILLER_WORDS = ["um", "uh", "like", "you know", "actually", "basically", "literally", "so", "right", "okay"]
```
Document in `docs/ml-feature-notes.md` that this is a deliberately simple, case-insensitive,
word-boundary substring match for Week 2 — Aho-Corasick or a more nuanced context-aware matcher
(to avoid over-counting "so" and "right" when used non-filler) is explicitly Week 3 polish
("improve speech-analysis reliability"), not Week 2's job.

### 3.4 `app/features/fluency.py`

Hand-rolled, NumPy/plain-Python, no shortcuts:

- `compute_wpm(words: list, duration_seconds: float) -> float` — count words, divide by
  `duration_seconds / 60`. Use **active speaking time** (duration minus total silence from
  `energy.py`'s `detect_silence_segments`), not raw clip duration — document this choice, it
  matches the original technical spec's "WPM... over active speaking time."
- `count_filler_words(full_text: str) -> dict` — case-insensitive word-boundary matching against
  `FILLER_WORDS`, returns `{"totalCount": int, "byWord": {"um": 3, "like": 5, ...}}`.
- `compute_fluency_score(wpm, filler_count, silence_stats, pitch_stats) -> dict` — **this is the
  one place real scoring/aggregation logic is introduced, which was explicitly out of scope in
  Week 1.** Write a simple, transparent, documented formula — e.g. start at 100, subtract fixed
  penalties for: WPM outside a healthy range (document the range and its source), filler-word
  density above a threshold, silence ratio above a threshold. **Every constant must live in
  `core/constants.py` with a comment explaining the number.** Return:
  ```python
  {
    "score": 78,
    "wpm": 142.3,
    "fillerWordCount": 6,
    "fillerWordBreakdown": {"um": 3, "like": 3},
    "silenceRatio": 0.18,
    "breakdown": { "wpmPenalty": 10, "fillerPenalty": 8, "silencePenalty": 4 }
  }
  ```
  The `breakdown` field matters — a score with no visible reasoning is exactly the kind of
  black-box the build-from-scratch policy exists to prevent. Document the full formula in
  `docs/technical-scoring-design.md`.

### 3.5 `app/features/confidence_sample.py`

`generate_sample_confidence() -> dict` — returns a **fixed-shape, clearly-labeled** sample
response matching what real video-based confidence scoring will eventually return:
```python
{
  "isSample": True,
  "score": 72,
  "eyeContactPercent": 68.0,
  "headStability": "moderate",
  "note": "Sample data — real video-based confidence scoring is not yet implemented (see docs/week2-report.md open concerns)."
}
```
This must NOT vary per request in a way that looks like real computation — use fixed or lightly
randomized-within-a-documented-range values, and the `isSample`/`note` fields must always be
present so nobody downstream (frontend, a grader, future-you) mistakes this for real output.

### 3.6 `POST /api/v1/evaluate` (new endpoint, `app/api/endpoints/evaluate.py`)

Accepts the same wav upload as Week 1's `/audio/features` (reuse `audio_loader.py` unchanged).
Internally calls the Week 1 feature extractors (`energy`, `pitch`) plus the new `transcript` and
`fluency` modules, plus `confidence_sample`. Returns:
```json
{
  "durationSeconds": 45.2,
  "fluency": { "score": 78, "wpm": 142.3, "fillerWordCount": 6, "fillerWordBreakdown": {}, "silenceRatio": 0.18, "breakdown": {} },
  "confidence": { "isSample": true, "score": 72, "eyeContactPercent": 68.0, "headStability": "moderate", "note": "..." },
  "transcript": { "fullText": "...", "wordCount": 107 }
}
```
Does not replace `/api/v1/audio/features` — both endpoints exist side by side.

(`new MediaRecorder(audioOnlyStream, { mimeType: 'audio/webm;codecs=opus' })` — construct a

stream feeds a `<video>` element with `muted` for self-preview). Exposes
`{ status, startRecording, stopRecording, recordedBlob, elapsedSeconds, error }`. Enforces the
300-second cap client-side (auto-stop at the limit, not just a warning) as well as the backend
cap.

### 4.2 `RecordingPage.tsx`
Requests permissions on mount with a clear pre-permission explainer (don't just slam the browser
prompt with no context). States: `idle` -> `permissionRequested` -> `ready` -> `recording` ->
`uploading` -> `complete` -> `error`. Shows `RecordingTimer`, `AudioLevelMeter` (live mic level
via `AnalyserNode`, not from the recorded file — this is real-time visual feedback, not stored
data), and `RecordingControls` (start/stop, re-record before upload). On stop, shows a preview
player for the recorded audio blob before committing to upload — the candidate should be able to
discard and re-record. On upload, show real progress/loading state reflecting that analysis can
take up to a minute (per ADR-010) — not a generic spinner with no context; tell the user what's
happening ("Transcribing your response...").

### 4.3 `ResultsPage.tsx`
Displays the returned `fluency` and `confidence` blocks. **The confidence card must visibly
indicate it's sample data** — don't hide `isSample` from the UI; render it as a labeled banner
("Sample data — full video-based confidence scoring is coming in a later week"), not fine print.
Fluency results render the real `score`, `wpm`, filler word breakdown, and the `breakdown`
penalty object in human-readable form (e.g., a small table or list, not just raw JSON).

### 4.4 `recordingService.ts`
`uploadRecording(blob: Blob) -> Promise<Recording>`, `listRecordings()`,
`getRecording(id: string)`. Uses the existing `apiClient.ts` — multipart upload needs
`Content-Type: multipart/form-data`, let axios set the boundary automatically (don't hand-set the
header, that breaks multipart boundaries — a real, common bug, watch for it).
